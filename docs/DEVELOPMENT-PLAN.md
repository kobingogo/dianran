点染已从上游无限画布发展为「快速生成 → 结果复用 → 画布迭代 → 按需 Agent」的本地创作工具。后续最有价值的工作是先确保作品可靠保存、请求与快照一致、任务可恢复，再推出可审阅的工作流执行。继续整体换肤、重写 Composer 或增加更多首页入口，不是当前主线。

本报告以 `origin/phase6-composer` 的 `19ada4e` 为实现基线，结合当前 main、5 个未合并 PR、用户提供的根目录 INTERACTION-PLAN.md 和仓库 docs/phase6 文档逐项核对。根目录附件保留原样。附件是设计方案，其「本次不运行测试」「本轮没有实现功能」等历史说明不作为本次任务的执行指令。

|---|---|---|

| 创作输入 | Composer 管提示词、附件、模式、chips；草稿按模式、画布和节点区分 | `components/composer/composer.tsx`、`stores/use-composer-store.ts` |
| 请求规划 | 能力表解析模型/渠道，提交冻结参数，浏览器直接调用服务商 | `lib/composer.ts`、`lib/model-capabilities.ts`、`services/api/` |

| 执行与恢复 | 画布页面负责生成、部分成功、重试、视频轮询、停止本地等待 | `pages/canvas/project.tsx`、`services/api/video.ts` |
| 数据 | Zustand + localforage/IndexedDB；媒体通过 storageKey 引用，支持 ZIP 与可选 WebDAV | canvas store、image/file storage、canvas-export、app-sync |

| 内容供给 | X/GitHub/Civitai 抓取、评分、精选、静态快照 | `brand/pipeline/`、`web/public/prompt-sources/` |
| 可选站点 API | `/api/usage` 写匿名提示词次数到 Vercel Blob；Docker 静态镜像不运行该函数 | `api/usage.js`、`vercel.json`、nginx |

核心生成路径：草稿 → 能力归一化 → 提交身份/参数快照 → 工作台或画布执行 → 本地媒体保存 → 结果来源记录 → 下一轮编辑。工作台「送入画布」只导入结果和 creation 元信息；画布 Composer 则在提交时建立素材、配置、结果关系，两者目前没有完整过程互通。

Agent 路径：显式上下文与会话 → 本地服务执行 → 结果按 threadId/turnId/itemId 物化与定位。当前保留独立输入组件和协议，不是三个模式共用同一个完整执行层。

## 4. 当前主要问题与优先级

### A. 保存可信度，优先级最高

`use-canvas-store.ts` 的存储写入有 400ms 防抖，回调内不等待并反馈写入结果；顶栏已可显示「已自动保存」。`localforage-storage.ts` 在 IndexedDB 异常时退到 localStorage，与业务数据默认不得保存到 localStorage 的规则不一致。刷新窗口、配额耗尽、写入异常均需要显式处理。此问题位于基础存储机制，不能归因于所有 phase6 逻辑，但它阻止宣称 P1 完整可靠。

### B. 验收证据不随仓库交付

PROGRESS 引用 acceptance.mjs、canvas-p1-*.mjs、JSON 与 `/workspace/dianran-shots` 截图；当前 docs/phase6 仅有两份 Markdown。已有 23 项前端测试主要验证规划和纯函数，没有覆盖组件交接、重复提交、复制入口和真实持久化失败。本次发现两项缺陷说明「单测绿」不足以替代浏览器闭环。

### C. 内容身份与统计信号

中文去重和重复 ID 本轮已修复。后续需在流水线生成 PR 前校验唯一 ID、内容身份、封面存在和 manifest 数量。`usage-stats.ts` 先删除队列，sendBeacon 返回值只能说明接收排队，fetch 也未确认成功；网络失败、服务器 429/502 会丢次数。它是参考信号，不适合直接成为内容价值的唯一依据。

### D. 对外说明与部署边界

前端 AI 仍直连用户渠道，作品主要本地保存，可选 WebDAV。与此同时 #4 已增加 Vercel 匿名统计函数；README 的「不经过任何服务器」需明确限定数据种类。Docker 只有静态站点与 SPA fallback，`/api/usage` 不具备同样行为。静态封面、插件、模板路径和 API 路径应分别验收，不能把 Vercel 可用等同于 Docker 完整可用。

### E. 维护与性能

画布页面约 3592 行，承担编辑器、生成执行、引用同步、任务恢复与快捷键。P2 若直接继续叠执行器，维护风险会上升。建议只在实现工作流时提取已真实复用的执行/恢复逻辑，不先做全仓重构。主入口约 1.011MB，React vendor 约 284KB；构建仍提示 Agent/Composer store 同时静态/动态导入，不能仅加 import() 就宣称拆包生效。

canvas-agent 生产依赖 npm audit 报告 7 项（3 high、3 moderate、1 low）。这是锁定依赖的扫描结果，尚未逐项确认点染运行路径可达性；安排专门维护提交评估与升级，不能直接等同于已发现可利用漏洞，也不自动执行大范围 audit fix。

## 5. 后续开发顺序

以下工作量按单人熟悉 TypeScript、可复用既有实现的前提估算，单位为有效开发工作日；不包括等待用户真实渠道验收。

| 阶段 | 交付与范围 | 核心验收 | 估算 |
|---|---|---|---|
| S0 PR 收敛 | 批准后按依赖整合 5 PR 与本轮修复；补最小 CI 和数据检查 | main 与最终审查提交一致，检查可复现；流水线不产生重复 ID，复制副本无原任务 | 1–2 天 |
| S1 P1 可靠性闭环 | 保存反馈、失败重试/导出、文件引用生命周期；统一验收重试/再生成与视频恢复 | 保存成功才显示成功；配额失败保留内存工作并允许导出；查询只 GET；原快照不被新草稿改写 | 3–5 天 |
| S2 首个 P2 切片 | 工作台可选「连同创作过程送入」；保留默认仅结果 | 输入+配置+结果及来源一次落图；相同投递不重复；本地媒体可导出导入；旧结果保留 | 2–3 天 |
| S3 可复用工作流 MVP | 基于已有配置和关系，先支持明确选定的生图/视频子图；执行前计划与手动确认 | 展示范围/依赖/实际参数/调用数；环和缺失输入阻止执行；改上游不自动调用；部分失败不覆盖成功 | 4–6 天 |
| S4 工作流模板与偏好 | 保存配置子图，实例化独立节点，展开明确参数，换模型重新校验 | 两次使用互不覆盖；来源与参数可追溯；模板不含 Key/临时任务/blob URL | 2–3 天 |
| S5 Agent 多步骤计划 | Agent 输出可审阅步骤，复用 S3 执行路径与现有权限 | 批准范围等于执行范围；定位目标节点；中断后不重复付费步骤；切会话不串结果 | 3–5 天 |

推荐第一轮只承诺 S0+S1+S2，约 6–10 个有效工作日。S3 在可靠性验收通过后立项；报价与历史耗时、批次对比作为后续独立切片，暂不阻塞创作主线。

### S1 可直接开工的任务

1. 在现有 canvas store 增加保存中/成功/失败信息，成功由真实持久化回执驱动；失败提供再次保存与 ZIP 导出。既有防抖值不顺手更改。
2. 为已引用媒体建立可验证的保存/删除/导出链路，保留原存储名和核心字段；业务写入失败不悄悄退到 localStorage。
3. 覆盖原快照再生成、失败槽位重试、配置修改后生成、源节点删除后生成，显示参数与请求一致；不引入第二套快照模型。
4. 将首页交接、画布建图/分支、复制、副本、视频中断恢复的模拟浏览器验收纳入仓库，覆盖 1440/390 和深浅主题；重点验证零重复 POST。
5. 真机/真实渠道验收与本地 Agent 恢复使用独立清单，明确需要用户提供的渠道和测试预算，不默认发起付费调用。

### 工作流 MVP 的限制与实现方向

优先沿用现有 Config 节点、关系 kind、creation/inputSnapshot 和生成 API。输入关系与生成关系组成执行计划；普通视觉连线和旧的未标注关系不能直接全部解释成可执行依赖。先预检，再按依赖排序执行，记录每次运行身份与各步骤结果。运行节点、选定子图、下游是三个显式范围，不以改参数或拖线触发生成。

MVP 不同时扩展文本、音频、所有插件和任意 Agent 工具。所选图包含不支持的节点时明确告知，不能静默跳过。调用数按已有工作台/画布执行方式计算，报价没有来源时仅显示渠道计费。新增超时、重试、并发或参考数量的行为边界单独说明后再确认。
