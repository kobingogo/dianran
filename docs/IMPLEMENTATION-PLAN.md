# 点染产品改进实施计划

## 目标与执行基线

依据 [产品分析报告](PRODUCT-REVIEW.md)，先解决作品损失、保存不一致和备份不完整，再收敛请求恢复与信任边界，让用户完成“生成—比较—采用—复用—备份”的完整任务，最后决定扩展投入。

本计划采用 R0–R5 阶段与 T00–T17 基础任务编号；本地 Agent 接入补充 AG01–AG10，其中 AG07–AG10 接通本机 Codex 生图并预留 Grok Build 等其他 Agent；Cloudflare 迁移与域名上线补充 CF01–CF06 专项任务，按关联阶段实施，避免和 phase5、phase6 的 P0/P1 混淆。首次执行前重新核对代码与 PR 状态。

- 主线基线：`ff457998e082889ad8d885da63c8de91c60f27ad`。
- 草稿 [PR #1](https://github.com/kobingogo/dianran/pull/1) 基线：`64e7dbed49cc84ba0851b038f052b0249cf5130d`。其四模式工作流、资源快照、参数预设、模板 ZIP、比较、来源报价与历史耗时已选择性整合到当前工作区；PR 本身仍未合并，整合验证见 [T11 记录](T11-INTEGRATION-VALIDATION.md)。
- 报告确认的三个缺陷：媒体清理遗漏视频历史、素材降级后读取旧列表、项目导出静默跳过缺失文件。其他风险先补复现与范围核对，再按任务处理。

- 原有提示词流水线与待验收文档存在未提交改动，执行时保留。修复与开发使用独立分支，不能把用户改动一起提交。

默认按阶段推进。同阶段中明确独立的任务可分别准备，但不默认增加人员、Agent 或新的任务线程。

## R0：建立可靠的执行起点

### T00 版本对齐与故障复现

**负责人：开发执行者；验收协作：项目负责人。依赖：无。投入：0.5–1 天。**

1. 核对最新 `main`、PR #1 head、CI 与未提交文件，建立任务状态表。
2. 将报告三个隔离实验转成可复用的针对性回归：保留视频历史文件、存储失败后恢复读取、缺件 ZIP。
3. 在独立测试页面构造两标签页与两设备清单，核实 T04/T10 的覆盖路径；不使用用户作品复现。
4. 列出所有写入与清理入口，以及所需的权威引用来源：素材、画布、草稿、生成历史、模板、运行快照和进行中的媒体提交。
5. 记录 PR #1 与基础修复是否触及相同文件，决定先合入基础修复还是在草稿分支准备后续整合。
6. 将 Codex 专项的项目切换、请求过期、完整内容读取实验整理为回归依据；补保存失败、失效操作与交互请求场景，按实际重叠范围重估投入。
7. 核对 Cloudflare 账号与资源可用性、拟用域名及现有发布脚本，拆出可先准备的代码和需要账号、购买、授权或发布才能完成的事项。

**通过条件：** 三个已确认缺陷有独立数据与预期；跨页、同步风险有明确复现场景或记录为待验证；没有把草稿功能记成线上已发布。

**产物：** 必要回归记录、变更基线及 PR 依赖说明。沿用现有 `web/tests/`、浏览器脚本与验收记录，不新建另一套测试框架。

## R1：先把作品保住

### T01 补齐媒体引用与清理保护

**依赖：T00。投入：1–2 天。对应报告：A1。**

**修改范围：** `web/src/services/file-storage.ts`、`image-storage.ts`、`web/src/stores/use-asset-store.ts`，以及读取引用来源所需的现有入口。

- 让媒体清理和图片清理覆盖相同的业务引用来源，补视频历史、草稿及其他真实媒体持有者。
- 提取确实复用的引用扫描函数；保留现有存储身份，不建立数据库式引用计数系统。
- 权威来源读取失败时停止本次清理，并提供可诊断信息；不能把读取失败当作空列表。
- 媒体从写入到业务记录落盘之间也要受保护：先避免清理进行中的文件；与 T04 统一处理跨页提交和清理竞争。

**验收：** 视频仅在历史中、媒体仅在草稿/模板/运行快照中时，删除无关素材并刷新，内容仍可打开和导出；读取历史或模板失败不触发删除；真正无任何引用的构造文件仍可清理。

**交付界限：** 单页引用修复可以先形成 PR，但不能把跨页误删宣布解决；完整通过依赖 T04 的竞争场景验收。

### T02 素材保存采用单一权威存储与真实回执

**依赖：T00；删除场景与 T01 联验。投入：1–2 天。对应报告：A2。**

**修改范围：** `web/src/stores/use-asset-store.ts`、相关素材操作入口、现有保存队列；只在必要处调整 `localforage-storage.ts`。

- 素材业务列表使用明确的 IndexedDB 路径，取消该路径的静默 localStorage 降级。
- 沿用保存队列思路，保留最新待保存快照，提供失败、再次保存和必要的抢救出口。
- 新增、编辑、删除、导入的成功提示由持久化回执驱动；失败时保留内存内容，不能误报已保存。
- 读取失败不能初始化空列表后覆盖原值；删除后的媒体清理须遵守已提交状态，不能早于可靠写入。
- 不批量修改主题等小配置存储。项目未上线，不增加旧列表字段兼容或自动迁移分支；演示/测试数据先独立备份。

**验收：** 注入一次写入失败，权威旧列表保留、新状态可重试；恢复后保存并刷新能读到新列表；读取失败不写空数据；失败删除不会清理仍被原记录持有的文件。

### T03 明确完整备份与抢救导出

**依赖：T00；与 T01/T02 联验。投入：1–2 天。对应报告：A3。**

**修改范围：** `web/src/lib/canvas/canvas-export.ts`、现有导入入口和导出 UI；模板 ZIP 接口仅补一致性所需改动。

- 导出前核对项目声明的原始媒体，形成可用与缺失清单；远程链接单独标注，不能默认等同于已打包。
- 完整备份缺件时给出明确信息；用户仍可主动导出抢救包，但文件和界面要说明缺失内容。
- 沿用现有 ZIP/清单工具与版本规则，导入后核对文件身份及引用，不能只确认 JSON 可解析。
- 导出失败不改变当前项目；保留保存失败时的抢救能力。

**验收：** 正常备份在独立空存储环境恢复原文件、参数与关系；故意缺失一个文件时完整备份不能误报成功；抢救包明确列出缺件；模板和项目导出对“完整”的含义一致。

### T04 保护多标签页写入与跨页清理

**依赖：T00–T03。投入：2–3 天。对应报告：A4，并补齐 A1 的跨页边界。**

**当前方案：所有页面直接编辑，按记录核对基线并原子保存。** 已按用户要求停用只读及编辑权交接。不同记录的修改合并，同一记录编辑/删除冲突保留双方数据并提供副本或备份恢复；自动清理避开其他页面的未保存引用。实现与待验收范围见 [多页面冲突保护](MULTI-PAGE-CONFLICT-PROTECTION.md)。下面首轮单写入条目仅保留历史背景，不再作为当前验收标准。

- 先盘点目标浏览器的跨页锁能力，复用平台能力，不添加经验性租约超时或自动抢占时间。
- 写入资格覆盖画布、素材、草稿、历史、模板、导入、同步和媒体清理。只读页可以浏览、下载，不得从后台恢复入口偷偷写入或发起新的付费生成。
- 主页面关闭后正常释放资格；其他页面获得资格前重新读取最新权威状态，不能把原先的旧集合直接写回。
- 交接必须先保存成功；保存失败保留当前编辑，不强行抢占。无法建立可靠保护的浏览器必须明确提示，不能悄悄降级成多页无保护。
- 如果目标用户需要多个可写页面，改为按业务记录的修订校验与原子冲突检测，重新估算；不在本任务同时实施两套方案。

**验收：** A/B 页面修改同项目或不同项目，不静默覆盖；只读页不创建任务、不执行清理；主页面刷新、关闭、保存失败与交接时状态可解释；新媒体写入与清理竞争不会误删文件。

**R1 完成标准：** 三个缺陷回归通过，多页保护场景通过，独立环境恢复完整备份成功；所有实际功能完成项进入 Pending Tests，仍不能写成用户已验收。

## R2：收敛本地服务和扩展的权限

### T05 本地代理调用授权与目标绑定

**当前状态：已实现待用户验收。** 配对、来源/目标校验和浏览器恢复提示已落实，12 项针对性行为检查与独立 Chromium 模拟渠道验收通过。代理 0.2.0 软件包已准备，尚未发布 npm 或部署前端；真实渠道、正式站点本地网络权限和成对发布仍待完成，见 [T05 验收记录](T05-PROXY-VALIDATION.md)。

**依赖：T00，可独立于 R1 准备。投入：2–3 天。对应报告：A7。**

**修改范围：** `canvas-proxy/index.js`、代理说明、`web/src/services/api/local-proxy.ts`、配置页与 `withLocalProxy` 调用路径。

- 保留本机监听，给浏览器调用增加配对凭据与允许来源校验；凭据不放入目标 URL、日志或普通配置分享文件。
- 将可转发目标绑定到用户授权的渠道/服务地址，保留被明确授权的本地模型；目标变化重新授权。
- 来源、目标与重定向规则在真正转发前检查，不能只限制响应 CORS。
- 预检只提供必要响应，不能凭预检自动授权来源；拒绝授权和本地网络权限失败要有中文解释。
- 不新增超时、体积或并发阈值。确有需要时单独提出适用环节、默认值与失败处理。

**验收：** 正常点染渠道可请求；伪造来源、缺失凭据、未授权目标无法转发；授权本地模型正常；错误或重定向不会绕过目标边界；拒绝浏览器本地访问权限后能找到下一步。

**发布依赖：** 前端与代理协议必须成对交付；先准备可审阅代码与软件包，npm 发布、线上部署另作为实际发布动作处理，不能只有前端更新导致现有用户无法连接。

### T06 插件安装前授权与脚本凭据范围

**当前状态：** 已实现待用户验收。安装/更新先审阅精确源码与摘要，默认脚本凭据限于绑定渠道；记录见 [T06/T16 验收](T06-T16-VALIDATION.md)。

**依赖：T00。投入：1–2 天。对应报告：A8。**

**修改范围：** `web/src/lib/canvas/plugin-loader.ts`、插件管理器、`web/src/services/api/model-plugin.ts` 与调用脚本说明。

- 插件源码在获得安装授权前不执行；展示来源、内容摘要和现有高权限提示，明确更新是否改变内容。
- 保持已安装源码快照可核对，更新不等同于无条件信任新版本；不在这一批建设签名平台或插件市场。
- 模型辅助 HTTP 接口只对绑定渠道附带默认凭据。向其他地址请求时必须显式处理凭据，不能自动复制渠道 Key。
- 保留用户自己编写的开发脚本，明确其高权限；不宣称已通过 Worker 或声明参数实现沙箱。

**验收：** 下载源码但取消安装时，源码副作用未发生；更新后的来源/摘要可核对；跨站辅助请求不含渠道 Key；现有同渠道脚本仍工作。

## R3：让请求状态与配置状态可信

### T07 区分失败、结果未知、查询恢复和新请求

**当前状态：** 已实现待真实渠道验收。未提交、明确拒绝与结果未知分开；意图先保存、任务 ID 先落盘，查询与新请求明确区分，见 [T07/T08 验收](T07-T08-VALIDATION.md)。

**依赖：T02/T04；复用既有工作流。投入：2–3 天。对应报告：A6。**

**修改范围：** 图片/视频 API、工作台历史、画布生成/重试入口、任务状态与工作流记录。

- 增加或明确“结果未知”语义：请求可能已被接受，但本地未收到可确认结果；不能将它直接等同于渠道拒绝。
- 保留已有“先保存意图、拿到视频 ID 后先保存再查询”的顺序；ID 落盘失败时保留可抢救信息。
- 查询沿用原任务身份与渠道；新建请求需要明确提示其行为与可能再次计费。
- 只按渠道实际能力接入请求身份、查询或幂等。渠道不支持时保留不确定状态，不伪造通用幂等保证。
- 原参数快照、成功槽位及 Agent 来源继续保留；不增加自动重试次数。

**验收：** 模拟远端已接受但响应丢失、返回任务 ID 后本地写入失败、查询中断、渠道明确拒绝；刷新不自动重提未知请求；用户能分辨“取状态”与“重新生成”；停止本地等待不被描述成取消远端任务。

### T08 按生成模式表达就绪状态与首次成功

**当前状态：** 已实现待用户验收。就绪按渠道/Key/模型/能力隔离，区分配置、模型读取与主动生成成功；不付费探测，见 [T07/T08 验收](T07-T08-VALIDATION.md)。

**依赖：T07；T00 后可先准备界面。投入：1–2 天。对应报告：P2。**

**修改范围：** onboarding、渠道能力与默认模型选择、首页和 Composer 状态。

- 状态区分“已配置”“已读取模型”“该能力有成功记录”，不把非空配置直接称为已验证连接。
- 就绪判断针对当前模式与选定模型；仅有文本模型不代表生图或视频可用。
- 原配置向导继续复用；配置完成后明确下一步作品任务，而非新建另一套向导。
- 不后台发起付费探测。首次成功来自用户主动提交的创作；未配置时能理解演示与真实生成的区别。

**验收：** 文本渠道进入生图时提示缺少对应能力；错误 Key 与模型读取成功但生成失败分别说明；切模型后旧成功记录不被当作新模型验证；未配置渠道时默认模型 chip 不误导可调用状态。

**依赖：AG01；结合 T08 的模式能力和 T12 验收。修改范围：** 画布工具描述、内容读取与本地媒体传递路径。

- 保留摘要读取，增加按节点读取完整正文的明确工具；读取/导出快照说明是否包含摘要，不能将截断内容冒充完整内容。
- 图片读取复用用户授权、原文件与现有附件传递；让 Agent 能按节点身份取得实际视觉内容。浏览器 blob 地址不能直接当成本机可读图片。
- 视频和音频只声明已实现的读取能力；若提供截图/文字结果，明确它们的范围，不以节点元数据代表已理解全部媒体。
- 按当前模式提供模型与参数能力，避免凭工作台配置推断全部画布能力。读取不返回渠道 Key。
- 不默认将整幅画布原文件发送给模型；引用授权与实际发送内容在执行说明中明确。

**验收：** 长文本末尾的指定内容可完整读取并准确修改；原图可通过已授权路径供 Codex 查看，缺件明确失败；新生成结果身份和来源可核对；未支持的媒体读取明确报告限制。

### AG05 校验批量操作并保护后续编辑

**依赖：T00/AG01；校验与 AG03 联验。修改范围：** `canvas-agent-ops.ts`、已有 schema 与画布历史/撤销入口。

- 对节点身份、类型、尺寸、引用、连线端点和可修改字段做业务校验，不能只接受任意 patch；不存在的更新对象、重复 ID 和失效连线返回明确错误。
- 批量普通编辑先整体预检，再提交；生成作为单独的异步执行阶段，不能承诺远端生成与本地编辑可以一起回滚。
- 返回实际生效动作和失败信息，Agent 能核对原意与结果。
- 撤销按现有历史能力保护其后的用户修改和生成结果；不能无条件恢复整份旧快照。

**验收：** 批次含无效动作时不会留下未声明的部分变更；合法批次结果可核对；Agent 修改后用户继续编辑，再撤销 Agent 操作不会静默抹掉用户新内容；撤销不声称取消远端生成。

### AG06 接通结构化提问与 MCP 交互请求

- 官方 [app-server 文档](https://learn.chatgpt.com/docs/app-server) 用于核对交互流程；升级协议时复核生成 schema 和锁定版本，不因最新版文档存在某能力就宣称当前包已支持。

**验收：** 提问可选择、补充和取消；表单按实际 schema 提交；中断、切会话、服务重启和多页面回答不会重复或串答；命令/文件/权限审批原有路径仍可用。

### AG07 核验本机生成能力并定义 Agent 适配契约

- 给 Agent 一个独立标识，区分 Agent、实际工具及其执行后端。能力按文生图、图片编辑、文生视频、图生视频分别声明；参数、参考支持、状态查询与取消能力仅来自实际可用接口，不按 Agent 名称推断。

**验收：** 已连接但没有生图工具时明确不可用；仅有生图能力不显示生视频可用；能力未验证与真实成功分开。契约可用隔离替身承接另一 Agent，画布业务层不依赖 Codex 专有事件字段；模型 API 原路径继续工作。

**依赖：AG07/AG01–AG03；参考读取与 AG04 联验。修改范围：** 当前图片生成入口、生成 API 的来源分派、本地 Agent 服务、Agent 面板与画布结果写回。

- R2 经 Worker 读取时显式准备缓存策略，不假设绑定存储就自动缓存；缺失文件返回明确错误，不能由 SPA 回退成 HTML。
- 将模板媒体及需要独立更新的官方插件资源纳入同样的版本与来源核对；插件仍遵守 T06 的授权边界。

**验收：** 清单、全部库 JSON 和被引用文件可核对；图片可显示、下载及作为真实生成参考；一次素材更新无需重建主站；上传中断不切到缺件版本；切回旧清单能够恢复完整旧快照。

### CF03 迁移主站与发布流程

**依赖：CF02。修改范围：** Workers/Wrangler 配置、资源路由、CI/发布脚本与部署说明。

- 准备独立预览环境，隔离生产写入与统计；现有 `api/usage.js` 和 `@vercel/blob` 依赖不会随静态部署自动迁移，交由 CF05 处理。
- 发布从明确提交执行，保留构建/资源版本与可回退目标；实际构建由 CI 或用户执行，按项目约定不在本地例行构建。
- AI 请求仍走用户配置的渠道；本地代理和本地 Codex 保持用户电脑上的运行方式，不因主站迁移承诺云端代管。

**验收：** 预览站首页和 `/canvas/:id` 刷新正常；模板、提示词、插件、媒体路径和必要 API 返回正确结果；资源缺件/接口缺失不返回伪成功页面；旧部署可继续使用。

### CF04 正式域名、浏览器数据转移与 Agent 授权

**依赖：CF01/CF03/T03；Agent 验收结合 AG01–AG03。修改范围：** 网站入口、品牌/帮助链接、插件指引、域名切换说明。

- 明确浏览器数据按来源隔离：旧 Vercel 域名里的作品、素材和配置不会自动出现在新域名。引导在旧站备份，在新站导入，再核对作品和引用；不声称重定向能够迁移 IndexedDB。

**验收：** 正式入口 DNS/HTTPS 正常，主要链接无旧域名误跳；旧站备份在新站可恢复声明范围的文件、参数与关系；两个来源的数据差异可解释；新域名可连接本地 Codex，未授权来源仍被阻止。

## PR 与既有开发的接入方式

1. 基础修复优先从当前主线建立 `codex/` 前缀分支。T01、T02、T03 可各自形成小 PR；有真实依赖的任务在 PR 描述中写清前置提交。
2. PR #1 保持未合并；其功能已选择性整合在当前工作区用于审阅与测试，不能将该工作区描述为主线或线上版本。
3. T11 四模式、T12 文本/音频和 T13 比较能力以当前整合工作区验收；真实渠道、目标设备与生产环境仍按 Pending Tests 执行。
4. 如果 PR #1 先获批准，后续任务改以新的主线为基线，任务目标不变；重新检查冲突，不重复提交同一功能。
5. 任何合并 `main` 前，说明该 PR 的改动、验证、风险与冲突，并取得用户明确同意。准备提交不等于已经获得合并或部署批准。
6. 代理协议发布与前端部署须说明匹配关系。数据库变化、Agent 消息格式变化分别按项目规范处理；Agent 消息格式升级必须先备份，不受普通业务数据“不迁移”的规则替代。

## 完成定义与记录方式

每个任务按以下状态推进：

**待开发 → 实现中 → 已实现待验证 → 验证通过待用户验收 → 用户验收通过。** 另记录所在分支、提交与是否已合并，不能用“完成”混淆代码、发布和用户验收。

- 开发执行者负责实现、必要的故障回归、脱敏证据及 Pending Tests；项目负责人确认真实使用与输出质量。
- 仅补有意义的行为测试；复用现有测试和浏览器检查。不在本地例行执行语法检查或构建；相关检查由既有 CI 或用户执行。
- 存储故障、误清理、重复请求等高损失场景必须有针对性证据。文案小改动用界面核对，不写镜像实现的测试。
- 已实现任务从 TODO 移入 Pending Tests，并写用户可以操作的场景；用户确认通过后才更新正式 Features。
- 用户可感知变化在 CHANGELOG 的 Unreleased 用一句中文归纳；未实施的计划不写作版本功能。
- 每个 PR 保留最小回退范围。存在未落盘内容时先完整备份或抢救，不通过覆盖新数据来回退。
- 未改变的超时、重试、并发与大小值继续沿用；需要新增或调整时，先提出具体行为与失败处理，再取得确认。
