# 点染产品审视：架构、产品与用户体验

## 核心判断

点染已经形成了有价值的创作链路：用自己的渠道生成，把结果继续用作参考，在画布中保留配置、输入和作品，再把可重复的过程整理为工作流。统一输入、生成快照、部分失败重试、保存反馈和 Agent 消息归属，都值得继续保留。

目前最需要补足的是这条链路的可信程度。用户能否确认作品不会被误清理、备份可以恢复、失败重试是否重新付费，以及界面承诺的操作确实可以完成？这些问题会直接影响用户是否愿意把点染当作日常工具。

本轮最明确的发现有三项：**媒体清理漏算视频历史引用；素材存储降级后可能读回旧列表；项目 ZIP 导出会静默跳过缺失文件。** 三项都经过当前源码与隔离内存实验交叉核实。多标签页覆盖、WebDAV 冲突、本地代理授权边界和真实渠道兼容性也值得优先处理，但证据类型与这三项不同，正文分别说明。

产品方向上，建议暂时以“已有 AI 渠道、需要反复比较和复用创作过程的个人创作者”为主要用户假设。先证明一套创作流程比直接使用渠道页面更省心，再决定是否扩大到零基础大众用户、团队协作或无人值守自动化。这个定位是本报告的建议，需要用户研究确认。

### 五轮研究如何推进

| 轮次 | 研究问题 | 实际工作 | 对判断的影响 |
|---|---|---|---|
| 第一轮：事实盘点 | 哪些能力已经存在？ | 核对主线、草稿 PR、计划、TODO 与 Pending Tests | 排除“没有统一输入、没有备份、没有工作流、没有新手向导”等过时判断 |
| 第二轮：架构追踪 | 作品与请求在哪里变得不可靠？ | 追踪存储、清理、导出、生成、恢复、插件及本地服务路径 | 找到不同入口之间的可靠性差异，而非仅凭文件长度判断架构 |
| 第三轮：产品与使用路径 | 从进入到完成作品，哪里容易失去理解？ | 查看线上界面，按新用户、熟练用户和长期用户的任务审视；查阅同类产品官方资料 | 区分配置完成与成功生成、画布模板与可执行模板、保存与备份 |
| 第四轮：反证与实验 | 这些批评是否忽略了既有保护？ | 三个隔离实验；检查保存队列、视口裁剪、插件提示、Agent 鉴权等反证 | 确认三项具体缺陷；降低对性能、插件和后台执行的过度结论 |
| 第五轮：决策 | 哪些工作应先于扩展？ | 按作品损失、凭据暴露、费用不确定性、首次成功与复用收益排序 | 得出先修作品保全与信任边界，再收敛创作场景的顺序 |

以下“事实”指源码或界面可直接核实；“实验”指隔离条件下的观察；“推断”指由机制推导的风险；“假设”指仍需真实用户或设备检验的判断。五轮是连续复核过程，不是虚构的专家会议或用户访谈。

## 第一部分：技术架构师视角

### A1. 媒体清理没有统一计算全部引用，存在作品被误删的路径

**事实与实验。** 图片清理会读取 Composer 和图片、视频历史；媒体清理只计算调用方提供的数据与工作流模板。删除素材时，调用方传入素材、画布和额外素材列表，没有视频历史。视频工作台则把生成视频原文件保存到同一个 `media_files` 存储，历史序列化时只保留文件身份、清空临时 URL。[E01](#e01)

这形成了具体反例：用户生成视频，只留在历史中；之后删除一个无关素材，触发全库媒体清理；视频文件仍被历史引用，却没有出现在保留集合中。隔离实验中，真实清理函数确实把 `video:history-only` 加入删除结果。历史记录可能还在，但刷新后原文件已无法从本地恢复。内存中的临时 URL 还可能让问题延后暴露。

建议优先修正媒体引用集合，并让图片、视频、音频按同一套“仍被谁使用”的规则清理。短期复用现有清理实现即可，不需要先设计复杂引用计数系统。清理时无法读到某个权威引用来源，应保留文件并报告问题。

验收应覆盖：只在历史中的视频、只在草稿中的引用、工作流模板素材、运行快照、跨标签页刚创建的素材。删除无关素材并刷新后，这些内容仍可使用；明确删除最后一处引用后才可清理。**这是当前最优先的作品安全问题。**

### A2. 素材保存与画布保存遵循不同契约，降级写入会造成两份状态

**事实与实验。** 画布使用专门的 IndexedDB 存储和保存队列，失败时保留待保存状态，读取失败不覆盖原数据。素材库仍使用通用适配器：写 IndexedDB 失败后写入 localStorage；读取时只有 IndexedDB 抛错才读 localStorage。[E02](#e02)

如果 IndexedDB 里已有旧列表，某次写入失败后新列表进入 localStorage，下一次 IndexedDB 正常读取便会返回旧列表。隔离实验复现了“新列表已写入备用位置，但恢复读取得到旧列表”。即便备用写入成功，用户看到的成功也不能证明下一次读取会取到同一份状态。

素材业务数据应沿用明确的保存失败反馈和权威存储，避免静默切换保存位置；导入、删除、编辑都需要相应回执。已有画布保存队列提供了可复用的思路，但不宜为了统一而一次性重构所有 store。

验收重点是注入一次写入失败、保持原权威数据、显示未落盘状态、恢复后重试，再刷新确认新状态。这个问题不能用“浏览器本地保存本来就不可靠”解释，因为两份状态的选择规则由项目自己决定。

### A3. 项目备份缺少完整性结论，用户拿到 ZIP 不等于拿到可恢复作品

**事实与实验。** 项目导出遍历文件身份时，原文件不存在便直接跳过，最后仍生成 ZIP 并调用下载。草稿 PR 中的工作流模板导出遇到缺失原文件则明确报错。[E03](#e03)

隔离实验为项目提供一个缺失图片身份，结果仍进入下载流程；压缩包只含 `projects.json`，文件清单为空。这里确认的是缺失文件场景，不能据此说所有正常导出都损坏。远程 URL 资源是否完整打包也应单独验收。

建议项目导出先列出需要的文件及缺失项。完整备份与带缺失项的抢救导出可以同时存在，但界面必须说明区别；保存失败时仍应允许抢救现有内容。导入后应核对原文件、参数与引用，而不是只检查 JSON 能否解析。

同类设计可以参考 InvokeAI 的项目文件：其官方文档明确说明嵌入媒体的条件，也列出不会保存的模型和工作流状态。可借鉴的是备份范围的清晰表达。[InvokeAI 项目文件说明](https://invoke.ai/features/canvas/canvas-projects/)

### A4. 保存队列解决了单页面写入排序，尚未解决多标签页覆盖

**事实与推断。** 所有画布项目与删除记录保存在一个键中，每次保存序列化整个集合；保存队列在当前页面内运行。该存储路径没有项目修订号校验或跨标签页写入协调。[E04](#e04)

两个标签页从同一状态打开：A 修改项目甲并保存；B 修改项目乙，然后写出自己仍持有的整份列表。B 的列表可能把项目甲恢复到旧值。即使用户在两个页面操作的是不同项目，仍可能相互覆盖。这是代码机制支持的风险，本轮没有用真实浏览器作品进行覆盖实验。

先明确支持范围：如果短期限制为同一站点只有一个页面可写，其他标签页应提供占用提示与只读入口；仅限制同一个项目还不够，因为不同项目也共享整份保存集合。若需要多页写入，则考虑按项目保存，并在写入事务中校验修订号。只加广播或只加锁，仍不足以修复“拿旧快照依次覆盖”的问题。

同一个全量保存结构还会让单项目变化承担全库序列化成本。是否已影响速度需要测量；目前没有证据支持立即更换 Zustand 或重写全部存储。

### A5. WebDAV 是文件同步，当前冲突策略会丢弃同项目的一侧编辑

**事实与推断。** 同步按项目 `updatedAt` 选择整份对象，存在删除标记；上传清单路径没有条件写入校验。两台设备分别修改同一项目中的不同节点，也只会选择一份较新的项目，而不会合并两处修改；并发上传清单还存在覆盖窗口。[E05](#e05)

已有 WebDAV 能力应保留，但产品应说明冲突如何处理。建议先做冲突副本、同步前差异摘要和远端修订校验。检测到并发变化时保留双方，再让用户选择。文件冲突检测可以解决当前需要，不必因此马上引入实时协作或 CRDT。

跨设备同步也不能被等同于独立备份：同步可能把错误删除传播出去。正式承诺跨设备工作前，需要分别验证同项目并发编辑、时钟偏差、删除与编辑冲突、上传中断。

### A6. 付费请求仍有“远端已接受，本地不知道”的不确定窗口

**事实与推断。** 工作流会先保存运行意图，阻止自动重提已经开始的步骤；视频任务拿到 ID 后先持久化，再查询。这些措施正确。仍然存在创建请求已被渠道接受、响应却丢失，或任务 ID 返回后本地写入失败的窗口。[E06](#e06)

前端这时可能无法知道任务到底有没有创建。重新生成可能再次计费，单纯增加重试次数不能消除不确定性。幂等需要服务端参与，AWS 的相关设计说明也以这个响应丢失问题为出发点；点染不能假设每个 OpenAI 兼容渠道都提供同样契约。[幂等请求与安全重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

建议把“明确失败”和“结果未知”分开记录。渠道支持时保存客户端请求身份、渠道任务身份和查询入口；不支持查询或幂等时，重提必须明确表示会创建新请求。显示的请求数继续注明是逻辑生成数，协议回退等实际 HTTP 请求需在诊断中另行解释。

工作流协调目前依赖页面生命周期。对交互式创作，这可以接受，前提是关闭后暂停、回来如何继续都有明确说明。只有用户确实需要长时间离线执行，再考虑把协调任务交给可选本地服务；本地服务也不能替代渠道侧幂等。

### A7. 本地代理的调用方和目标授权需要收敛

**事实与条件性风险。** `canvas-proxy` 默认监听 `127.0.0.1`，但允许任意来源的跨域请求、任意方法与请求头，接受任意 HTTP/HTTPS 目标，未在转发前校验连接凭据或来源白名单。相比之下，本地 Agent 有 token 和来源检查。[E07](#e07)

当其他网页能访问这个代理端口时，它可以借代理转发并读取响应，包括对本地网络目标的访问。实际可达性受浏览器和操作系统策略影响；本轮没有尝试读取用户本地服务，也不把它写成已发生的数据泄露。代理本身也不会自动取得点染网页中的 API Key。

建议明确授权哪些网页可以调用代理、哪些上游可以被转发。保留用户确实需要的本地模型地址，避免简单禁止全部私网目标；对首次新增目标提供明确授权或绑定规则。

浏览器限制也属于兼容性问题。Chrome 官方已将本地网络访问纳入权限流程，线上 HTTPS 页面连接本地伴随服务需要单独验收。不能把所有连接失败都归为 CORS，也不宜让用户关闭浏览器安全保护来完成配置。[Chrome 本地网络访问说明](https://developer.chrome.com/blog/local-network-access)

### A8. 插件和调用脚本拥有页面权限，扩展机制需要明确分层

**事实与判断。** 节点插件通过下载源码、创建 Blob 并动态导入执行；安装过程先执行源码再检查导出结构。自定义模型脚本通过 `new Function` 执行，并获得 API Key；HTTP 辅助接口接受绝对地址且默认附带渠道 Authorization。插件管理器已经明确提示插件可访问本地数据和 Key。[E08](#e08)

因此不能说项目“没有告知风险”，也不能把执行用户自己编写的脚本直接定性为漏洞。但安装外部插件意味着信任其全部页面权限，而不是只授权它处理一个节点。外部代码可能读取数据、发出请求，禁用插件后的清理也无法自动撤销已经发生的副作用。

短期可先核对来源、固定版本或内容摘要，明确升级引入的变化，并避免 HTTP 辅助接口对任意跨站地址默认附带渠道凭据。面向非技术用户开放插件生态前，应区分素材处理插件、模型适配器和具备高权限的开发脚本。需要隔离执行时，必须同时设计受控凭据与网络桥接；Worker 本身并不自动形成完整权限边界。

OWASP 对第三方 JavaScript 的说明支持这一信任模型：页面内执行的外部脚本应按应用代码评估权限和供应链变化。[第三方 JavaScript 管理](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Javascript_Management_Cheat_Sheet.html)

### A9. 生成、重试、工作流和页面编辑仍相互耦合，维护风险集中在行为一致性

**事实与判断。** 主线画布页面约 3,641 行，同时处理编辑交互、请求控制、视频恢复、多类型生成、重试和工作流回调。现有代码也已经提取提交规划、能力解析、保存队列与工作流计划，不能只凭行数否定整体质量。[E09](#e09)

更有价值的判断标准是：新增一种模式时，是否必须分别修正普通提交、节点重试、工作流执行与历史恢复；这些入口是否都保持同一份输入、实际参数、结果归属和保存顺序。本轮发现的清理、备份与存储差异表明，跨入口的行为契约仍需要加强。

建议在下一次真实修改触及这些路径时，提取已经重复的执行与结果落盘逻辑，保留页面负责编辑器交互。先写清少量行为约束：批准参数等于请求参数；成功结果不被失败重试覆盖；未知请求不自动重提；文件仍有引用便不清理。无需先做全仓组件拆分或建立大型执行框架。

### A10. 测试基础已建立，但渠道、设备与规模方面仍有证据缺口

**事实与未验证风险。** 草稿 PR 的验收记录包含前端 45 项测试、261 断言及模拟浏览器场景；既有 CI 已成功。真实模型输出、渠道计费、Agent 恢复、手机键盘和 Docker 路径仍列在待验收范围。[E10](#e10)

画布已有节点与连线视口裁剪，也有图片预览缓存，不能说它无差别渲染所有原图。仍需测量首次加载、拖拽、全量保存、导出和存储用量扫描在作品积累后的表现。这里没有性能实测数据，不应给出“超过某个节点数必卡”的结论。

建议建立按渠道和模式标注的验收矩阵：参数被接受、产出与引用正确、失败行为可解释、刷新后可恢复、实际计费可核对。性能则从典型项目和重度项目取样，再决定优化方向；本报告不新增并发、超时或大小限制。

## 第二部分：产品经理视角

### P1. 产品同时服务多种成熟度的用户，主价值需要更明确

首页鼓励“一句话开始”；高级能力要求用户理解渠道、协议、模型能力、浏览器存储、节点和本地 Agent。这两种使用方式都能成立，但获取用户、引导和支持成本不同。[E11](#e11)

建议先选定一个主要任务，例如“上传产品参考，生成几个候选，比较后保留一个方向，扩成多种用途并备份”。用这个任务检验整个产品。图片、视频、文字与音频的广度应服务该任务，而不是成为各自独立的开发目标。

对已有渠道的个人创作者，点染的优势是过程可追溯、渠道可选择、资产可带走。对零基础用户，则还要解决从哪里取得 Key、如何判断服务能否用等问题。后者需要不同的产品投入，不能只依靠把高级设置隐藏起来。

### P2. 配置向导完成了连接信息收集，首次成功还没有成为清晰的完成条件

**事实。** 线上已有“选服务商—填 Key—识别模型”的向导，并包含读取模型失败的处理。首页的“已连接”判断却只是 URL、Key 与模型列表非空，并不证明选定生图或视频模型成功运行。[E12](#e12)

例如，一个仅配置文本模型的渠道可能满足首页已连接判断；用户正在生图时，实际所需能力仍未就绪。读取模型列表成功也不证明参考图编辑接口可用。

建议状态区分“已配置”“模型列表已读取”“该能力有成功记录”。由用户主动完成一次明确的创作操作，再把它作为首次成功；涉及费用时提前说明。不要用后台自动付费调用检验连接。

用户没有 Key 时，可以浏览或使用带示例素材的演示流程，理解价值后再配置。演示应明确标注，不能把预置结果伪装成实时生成。

### P3. 首页画布模板与工作流模板尚未形成统一的产品语义

**事实。** 首页模板介绍包含“一键出三种尺寸”；实际入口只创建带文案、配置与排版的画布，连接没有标记 `kind`。工作流则只把明确的输入或生成关系解释为执行依赖。草稿 PR 的工作流模板采用另一套计划结构、预检和文件打包机制。[E13](#e13)

首页模板不是毫无价值：正文中的节点引用可以承接素材，排版也减少了从空画布开始的负担。但“一键”承诺还需要核实入口、选取范围、参数和执行方式是否闭环。不能因为画面看起来连好了，就认为整条流程已经能够执行。

短期应说明模板会创建什么、用户下一步点哪里；再把最重要的首页模板接到已有计划预览入口。模板需要展示必填输入、所需能力、预计调用与示例结果，不能只展示布局缩略图。

ComfyUI 的模板先检查所需资源，再让用户运行；Figma Weave 的 Tools 则把既有工作流转成简化输入界面。点染可以分别借鉴“依赖预检”和“让使用者只填写必要输入”，无需复制它们的全部平台能力。[ComfyUI 模板说明](https://docs.comfy.org/interface/features/template)、[Figma Weave Tools](https://help.weavy.ai/en/articles/12267755-tools)

### P4. 比较能力已有进展，但“决定采用哪一版”仍需成为主线

草稿 PR 已加入只读比较和原参数展示，不能再把“没有比较功能”作为结论。问题是比较之后的决策如何保留：这一版为什么被选中、下一步沿用哪张图、交付哪一版、哪些结果只是探索候选。[E14](#e14)

这是用户研究假设，不是本轮证实的普遍痛点。先观察用户是否反复重命名节点、截图记录或在外部记事，再决定是否增加“采用”“待修改”等轻量状态。优先复用现有分组、主图与来源关系，不急于建立完整项目管理系统。

可借鉴 InvokeAI 将候选结果放在暂存区、由用户接受或舍弃的做法：生成结果与采用结果需要区别。点染的节点画布用途不同，但同样需要让用户看懂当前决定。[InvokeAI 候选结果与画布](https://invoke-ai.github.io/InvokeAI-7/users-guide/canvas/introduction/)

### P5. 提示词库的丰富度不能替代可用性与复现条件

线上示例含不同来源、不同模型习惯的提示词，部分含 LoRA 标记。数据结构虽有模型、尺寸及参考图字段，但并不能完整表达外部作品所依赖的全部设置。首页却使用了“复现”的表达。[E15](#e15)

用户把某条提示词复制到任意渠道，不能据此预期得到原图效果。即使同模型、同参数，生成也可能存在随机性或服务版本变化。建议把“获取灵感”“适用于某能力”“按原条件尝试”分开，让用户知道哪些条件缺失。

精选优先支持当前可用渠道与常见任务，并为少量重点示例记录实际试用结果。提示词的复制次数可以反映兴趣，不能被当作生成成功率或作品质量。采集流水线的发布门禁有价值，但它主要解决发布范围与内容筛选，不能证明提示词在用户渠道中有效。

### P6. 产品指标偏向访问和提示词动作，尚难解释创作价值

**事实与判断。** 已有页面访问统计、提示词复制与使用计数、任务中心请求状态；当前查看的统计路径没有形成首次成功、结果复用、采用作品和成功恢复的完整指标。提示词计数还是 best-effort：发出前清队列，失败没有响应确认，相关欠账已列入 TODO。[E16](#e16)

建议先定义“用户完成了什么”，再决定收集什么。可从本地诊断与少量自愿研究样本开始：首次成功生成、结果成为下一轮输入、一次任务得到可交付作品、备份恢复成功，以及一段时间后是否继续使用。

不要为了衡量产品而默认上传创作内容或增加账号体系；也不要把生成次数单独当作成功指标。用户可能生成更少、却更快得到作品。收费、规模化支持和团队服务等商业方向，应在这个价值得到验证后再决定。

## 第三部分：用户视角

以下用实际任务描述问题。引号内是待验证的用户疑问，不是访谈原话。

| 使用阶段 | 用户可能遇到的疑问 | 已有改善 | 剩余问题与证据性质 |
|---|---|---|---|
| 第一次进入 | “显示了模型，为什么还不能生成？” | 首页状态、配置向导、参数入口已存在 | 未配置渠道时仍显示默认模型；需要把默认选择与可调用状态解释清楚。界面事实＋理解假设 |
| 配置完成 | “已连接是不是代表生图和视频都能用？” | 模型读取、能力分配、错误处理 | URL/Key/模型非空不是按模式验证成功。源码事实 |
| 开始创作 | “同一个产品的几张图怎么保持一致？” | 参考图、生成快照、分支、过程投递 | 仅重复文案不能保证主体一致；模板需要引导参考关系与采用结果。任务假设，待真实模型测试 |
| 多次迭代 | “这一张为什么比上一张好，下一步该用谁？” | 原参数、来源、主图及草稿 PR 比较 | 候选、采用和交付状态仍需验证；四模式能力还未合并。产品假设＋版本事实 |
| 请求失败 | “重试会不会重新收费？停止后渠道还在做吗？” | 原快照重试、视频取状态、流程人工恢复 | 结果未知需单独说明；停止查询不等于取消远端任务。源码事实＋渠道限制 |
| 保存作品 | “已保存是不是就不会丢？” | 画布保存状态、失败保留、ZIP 与 WebDAV | 媒体误清理、素材降级读旧值、备份缺件，以及浏览器保存的保留边界。前三项有隔离实验证据 |
| 换设备或地址 | “为什么另一台电脑找不到画布？” | WebDAV 与导入导出 | 当前没有内置云账户；数据按浏览器来源隔离。域名/端口变化与设备变化都需要明确交接。机制事实 |
| 使用 Agent | “我只是想出图，为什么还要看终端、Token、技能？” | Agent 可选，连接说明已有 | 本轮会话中未连接面板显示较多安装内容；不代表所有新用户都会自动打开。是否抢占主任务注意力需观察 |
| 手机操作 | “上传后键盘会挡住操作吗？画布能否方便选节点？” | 手机 Composer、底部弹层已有 | 真机键盘、触摸冲突与长任务后台切换未验证，不能用桌面模拟证明。待验收项 |
| 搬走作品 | “导出的文件以后还可以继续用吗？” | 项目 ZIP、草稿 PR 模板 ZIP | 媒体缺失、模型替换、同步冲突与完整性结果需要可见。事实与验收缺口 |

对用户而言，“本地优先”意味着更强的作品掌控，同时要求产品把保存位置、备份范围与恢复步骤讲清楚。浏览器存储默认可能采用 best-effort 保留机制，站点可申请持久化，但持久化也不能防止用户主动清除数据。[浏览器存储与清理机制](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

当前已有存储用量查看，源码搜索未见持久化申请。建议显示保留状态和可验证的备份状态，而不是只显示占用空间。浏览器通常不会随意清理常访问站点，不能因此夸大丢失概率；误清理和备份缺件则是项目自身需要优先修复的行为。

首页“所有密钥与作品只存在你的浏览器里”也应收敛。README 已说明直接请求渠道、可选代理、Agent、WebDAV 和统计的边界，首页表达仍过于绝对。作品主要保存在浏览器，与生成时素材和 Key 是否发往用户选定的服务，是两个不同的问题。[E11](#e11)

## 第四部分：交叉讨论后的取舍

| 初始提议 | 反方意见与证据 | 复核后的决定 |
|---|---|---|
| 加云账户与后端，解决本地可靠性 | 误清理、降级读旧值和缺件导出会在有后端时继续存在；本地优先本身是产品优势 | 先修文件生命周期和备份契约；跨设备需求确认后再扩展 |
| 把工作流移到后台，保证不重复付费 | 后台可以改善页面关闭后的连续执行，但无法独自判定渠道是否接受了丢失响应的请求 | 先区分未知结果、查询与重提；按渠道提供恢复能力，按用户需求增加可选本地执行 |
| 重构大画布页面解决架构问题 | 已有共享规划、队列、能力表与裁剪；行数没有证明应重写全页 | 只抽取真实重复且涉及一致性的执行路径，用具体失败场景验证 |
| 新手需要一个更完整的配置向导 | 向导已经存在，继续增加说明可能加重理解负担 | 以第一次成功作品作为完成条件，按用户当前问题显示下一步 |
| 继续增加模型、技能和插件形成优势 | 已有四模式能力，但真实验收仍未完成；插件执行协议会继续扩大状态和信任范围 | 先收敛常用创作场景，再决定插件动作和技能扩展的投入 |
| 为安全彻底移除脚本与插件 | 对技术用户，适配不同渠道是有效需求；现有界面也已提示权限 | 保留高权限开发能力，明确授权和来源；大众插件另设受控接口 |
| 用生成次数和提示词复制次数衡量增长 | 更多请求可能只是失败或无效迭代；复制也不证明产出质量 | 衡量任务完成、复用和恢复，先从本地与自愿研究样本开始 |

由此得到一个更精确的方向：点染适合做**可以持续迭代、可核对过程、可带走作品的个人创作工具**。要扩大这个方向，先让上述三个承诺可验证。团队实时协作、全自动 Agent、广泛插件市场等方向仍可保留，但当前证据不足以支持它们先于作品保全。

## 第五部分：建议处理顺序与验收标准

这里的 P0 表示建议优先修复或收敛的高损失问题；P1 表示直接影响主创作路径；P2 表示依赖用户需求或测量结果的扩展。不是既有开发计划中的同名阶段，也不表示已把这些建议自动加入开发任务。

| 顺序 | 优先级 | 工作 | 做到什么才算完成 |
|---|---|---|---|
| 1 | P0 | 补媒体清理的权威引用来源 | 视频仅在历史中、素材仅在草稿或模板中时，删除无关素材并刷新仍可用；读取引用来源失败不执行误清理 |
| 2 | P0 | 统一素材业务保存契约 | 写入失败有可见状态，保持权威数据；重试成功后刷新读到同一版本，不再静默写到另一位置 |
| 3 | P0 | 备份完整性与抢救导出 | 导出前明确缺件；完整备份可在独立浏览器环境恢复媒体与引用；抢救包清楚标明限制 |
| 4 | P0 | 本地代理调用授权与目标边界 | 未授权来源无法使用转发；用户授权的本地模型仍能用；当前浏览器权限拒绝有可理解的反馈 |
| 5 | P0 | 收敛多标签页覆盖风险 | 两页修改不同项目或同项目时不静默覆盖；短期单页策略或修订检查必须明确 |
| 6 | P1 | 真实渠道与设备验收 | 代表性渠道完成生成、参考、失败、重试、刷新恢复与计费核对；手机键盘和 Docker 独立验证 |
| 7 | P1 | 请求未知状态与恢复操作 | 用户能分辨查询、重试失败槽位、重新创建任务；无查询能力时明确说明不确定性与再次计费可能 |
| 8 | P1 | 首页模板接入真实执行路径 | 从模板填写输入、预览步骤到运行有明确入口；执行范围、引用与宣传一致 |
| 9 | P1 | 配置状态与首次成功 | 文本渠道不被当作生图已就绪；配置后用户能完成第一次作品，并理解失败原因 |
| 10 | P1 | WebDAV 冲突保留 | 并发修改保留双方或明确阻止覆盖；同步摘要显示冲突和未完成部分 |
| 11 | P1 | 插件与脚本权限、来源与升级 | 权限范围、来源和变更可核对；辅助请求不把渠道凭据默认发送到任意目标 |
| 12 | P1 | 选定一个任务闭环并衡量价值 | 用户从参考到候选、采用、复用和导出完成任务；指标不依赖上传创作内容 |
| 13 | P2 | 性能与局部执行逻辑整理 | 先取得典型及重度项目数据，再改善实际瓶颈；验证跨入口行为一致 |
| 14 | P2 | 插件执行工作流、更多技能、本地后台协调 | 已验证用户确实需要；参数、权限、结果、恢复协议明确后再开发 |

第一批交付建议聚焦作品保全：清理、保存、完整备份和多页写入。代理授权可作为独立范围同时准备。第二批用真实渠道验证现有主线，并修正模板与配置状态。第三批再推进更广的插件执行和 Agent 能力。

这会调整原计划的优先次序，原因是本轮找到了此前没有收敛的作品损失路径。四模式工作流等已开发功能继续保留在待验收状态；本报告没有合并 PR、暂停开发或修改任何行为边界。

### 建议开展的用户研究

先邀请覆盖以下使用背景的真实用户，样本用于找问题，不用于推算总体转化率。参与者自行配置凭据，付费调用由其明确选择；研究只记录必要的操作与结果。

| 研究任务 | 要验证的假设 | 观察结果 |
|---|---|---|
| 有 Key、首次使用：完成一张产品图 | 用户能理解渠道与模型，并独立完成第一次成功 | 停顿位置、错误解释、求助次数、首次成功所需步骤 |
| 熟练创作者：比较候选并做一个分支 | 参数可追溯能降低重复试错，比较能帮助决定 | 是否找到原参考与参数，是否误覆盖旧结果，采用哪版是否明确 |
| 创作一个短片：遇到中断后恢复 | 用户理解查询与重提的区别 | 是否重复创建任务，是否误以为停止等于远端取消 |
| 长期使用者：在独立环境恢复备份 | 用户信任的“备份成功”与实际可恢复一致 | 缺件是否预先可见，原媒体、关系与参数是否可恢复 |
| 手机用户：上传、输入、查看结果 | 底部 Composer 能适应真实键盘与触摸 | 遮挡、焦点跳转、误触、后台返回后的任务状态 |
| 两设备用户：分别编辑后同步 | 冲突提示能保全作品且不增加过度负担 | 双方编辑是否保留，用户能否解释最终版本 |

不要预设“减少多少步骤”或“提升多少转化”的收益。先取得基线，再让用户比较修改前后的任务完成情况。若用户最常用的仍是单次生图，应优先简化该路径；若复用流程能持续节省时间，再扩大工作流投入。

### 三个隔离实验的条件与结果

实验读取本轮主线中的实际 TypeScript 源码，通过现有 TypeScript 运行依赖转换后在独立 Node 上下文加载。替换的只有存储、文件读取、ZIP 与下载接口；没有构建产品，也没有删除真实文件。它验证特定函数行为，不能代替整条浏览器使用路径的端到端验收。

| 实验 | 输入与替身 | 实际观察 | 结论边界 |
|---|---|---|---|
| 媒体清理 | 模拟媒体库中有 `video:history-only`；传入调用方相同形状的素材/项目数据；模板为空 | `removeItem` 收到 `video:history-only` | 确认不在当前引用集合中的历史文件会被删除；真实历史存储位置与调用路径由 E01 交叉核实 |
| 素材降级 | IndexedDB 原有旧值；注入一次写入失败；localStorage 写入成功；随后恢复 IndexedDB 读取 | 备用位置为新列表，读取结果为旧列表 | 确认两份状态之间没有保证读取最新值；不是对用户真实配额的测试 |
| 项目导出 | 一个节点引用 `image:missing`；原文件读取返回空；捕获 ZIP 项目与下载动作 | 下载动作触发；ZIP 只含 `projects.json`；导出文件清单为零 | 确认缺件时没有明确拒绝或完整性标记；不是所有 ZIP 导出都会缺件 |

后续端到端复现应使用独立测试浏览器与人工构造的数据，避免破坏已有作品。报告中的建议尚未实施；已检查 TODO 与 Pending Tests，本轮没有功能完成或删除，因此未移动待办、改写待验收项或增加版本变更记录。
